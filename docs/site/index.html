# 安德鲁牙科就诊与运营系统

当前版本 **3.1.0**。五个独立岗位门户，共享关系型 SQLite 数据库及 Node.js 后端；总部统筹连锁，店长管理机构分配的授权门诊。

课程设计成果：[1602240215.pdf](docs/design/1602240215.pdf)（2026-10-20 修订版，585 页）。文档围绕牙科连锁业务升级，包含行业调研、业务用例与详细流程、分析与系统设计、数据库模型和实施边界。完整页数、图表与数据库模型统计及 PDF 校验摘要见 [交付清单](docs/design/delivery-manifest.json)。

`docs/design/source/` 保留上一版可编辑源材料和图稿，尚未同步到本次 PDF 的内容模型，不能据此重建本修订版。设计文档描述目标方案；应用现状与真实环境验收状态以本仓库代码和对应验收记录为准。

- 顾客：`/customer/login`
- 前台：`/frontdesk/login`
- 医生：`/doctor/login`
- 店长：`/manager/login`（授权门诊）
- 总部：`/hq/login`（全部门诊）

## 本地启动

需要 Node.js **24.15.0** 或经过完整回归的兼容版本。

```powershell
cd andrew-system
npm ci
npm run build
npm start
```

访问 `http://127.0.0.1:3210/customer/login`。默认本机演示首次创建合成患者与五个演示账号 `chen`、`front`、`doctor`、`manager`、`hq`，密码均为 `Dental2026!`。员工入口没有公开注册。已有数据库不会重置；旧版结构自动迁移前会保存完整快照，运行中的旧服务会阻止升级。

正式新库设 `DENTAL_SEED_DEMO=0`，关闭演示数据与演示入口。该开关不会删除已有演示账号，正式数据必须使用独立数据库。首个总部账号通过 `tools/accounts.mjs create-staff owner hq` 初始化；总部登录后创建门诊，再为店长分配明确的门诊范围。

## 已实现的业务

- 患者资料、结构化过敏申报与工作人员核实；身份核验后查询、绑定顾客账号、版本受控归并与历史别名。
- 排班、预约、改期、取消、到诊、爽约更正；跨门诊牙医冲突与患者时间冲突检查；失败改期回滚。
- 治疗明细与价格快照、就诊完成冻结、带作者/时间/原因的不可覆盖附记。
- 费用开单、人工核对收款、欠款余额、原款限额退款、保留原单的冲销、按北京时间核对营业日资金与差额、来源变化失效提示。
- 成本录入审核、季度报告及基金测算；收入明确采用有效开单口径，另有收款账簿，不将两者混用。
- 员工创建、归属调整、启停与离职；撤销旧会话、保留有效总部账号、本人改密、机构核验后的限时单次恢复凭证。

现金/银行/POS 均为工作人员核验凭证后的人工记账，代码不执行银行转账或线上支付；恢复凭证由机构核验后交付，未接入短信。尚未提供完整牙位病历、影像、处方、知情同意、医保及正式票据，也未经真实临床或公网容量验收。

```text

server/repositories/          明确字段映射、批量关联、条件查询
```

当前38张表。十二类核心业务对象采用明确类型列，过敏、资格、治疗行、结算行、报告行等采用关系子表。`users.data` 保留身份对象兼容格式，同时以同步列和索引提供查询；审计及请求重放结果使用JSON快照。

日常前端使用 `/api/workspace` 按页面、筛选及分页读取，主区更新保留导航外壳。`/api/state` 保留给兼容验证；不用于日常整包刷新。写入检查权限、范围与版本，并支持同一逻辑操作幂等重放。

# 3.1架构与业务边界

更新日期：2026-10-19。当前实现保持原生浏览器模块、Node.js内置HTTP及SQLite，按职责组织代码。

## 请求与数据流

```mermaid
flowchart LR
    Portal[五岗位独立门户] --> UI[页面模块与公共组件]
    UI --> API[API客户端与页面状态]
    API --> HTTP[会话和安全校验]
    HTTP --> Query[分页查询服务]
    HTTP --> Command[岗位权限和事务业务服务]
    Query --> Repo[关系型Repository]
    Command --> Repo
    Repo --> DB[(SQLite与版本迁移)]
```

`public/app.js` 只安装入口和事件。页面、组件与API分离；路由、筛选、分页触发相应查询，保留导航及用户菜单，只更新业务主区。日/周日历按时间窗口分批读取完整结果，列表使用分页；预约与改期另有独立分页时段选择器。各页所需的关联实体由服务端批量补充。

样式源分为base、components、layout、staff、customer、auth、responsive、accessibility、print，通过明确的CSS layer顺序构建。重复规则由PostCSS/cssnano整理；普通主题不再依赖!important，减少动态及打印保留必要覆盖。

## 服务职责

| 模块 | 职责 |
|---|---|
| HTTP | JSON请求、Origin/Host、会话、CSRF、限流、幂等、静态资源 |
| policies | 顾客/前台/医生/店长/总部权限矩阵 |
| patients / patient-merge | 档案、身份核验、可追溯归并 |
| resources / appointments | 门诊资源、排班、预约和状态转换 |
| clinical / clinical-addenda | 治疗快照、完成冻结、追加附记 |
| finance / reports | 收退款、余额、冲销、日结与季度核算 |
| accounts | 创建、归属、在职状态、改密及核验恢复 |
| workspace | 按页SQL查询、关联补充、范围控制、聚合统计 |
| repositories | 白名单字段、SQL参数绑定、批量子表读写 |
| migrations | 版本、checksum、升级快照、事务和外键检查 |

医生可读其授权患者的跨门诊历史，预约列表及临床写入仍按本人责任控制。前台和店长按明确的clinicIds操作授权门诊；总部覆盖全部门诊。权限和数据范围在后端执行。

## 连锁职责与数据范围

| 岗位 | 数据范围 | 主要职责 |
|---|---|---|
| 顾客 | 本人档案与业务 | 注册、预约、自助改期取消、就诊及费用查看 |
| 前台 | 授权门诊 | 核对患者、预约与出席、排班、开单收款、营业日核对 |
| 医生 | 本人接诊及相关患者历史 | 记录治疗、完成诊疗、追加更正附记 |
| 店长 | 明确分配的门诊 | 门店患者与接诊、排班、诊疗与附记、收退款及冲销、日结、成本登记审核和履约统计 |
| 总部 | 全部门诊 | 统一资源、全部员工授权、患者主档归并与账号绑定、全链季度核算批准、全局规则、审计和业务导出；可处理跨店业务 |

店长看不到总部账号管理、全链审计与系统设置页面，不可核算或批准全链报告；其成本、账务、患者关联与预约统计均由服务端限制门诊范围。隐藏按钮只是界面表现，直接调用接口仍须通过同样校验。

## 存储与一致性

38张物理表包含十二类核心对象、关系子表、身份与审计、迁移记录、账簿、恢复及幂等信息。核心业务表不再使用每实体一个data JSON字段。用户身份对象保留兼容data，并以同步列查询；审计、幂等响应及历史签名使用快照形式。

Repository提供get/find/query/count及批量关联映射。所有修改使用同步事务，嵌套调用使用savepoint；金额以整数分处理。版本冲突返回409。账簿、诊疗附记和审计以追加记录留痕，完成治疗和原结算快照不被后续修改覆盖。

同一逻辑写入的Idempotency-Key及财务操作键检查内容hash，在事务内保存结果；重放返回原结果，内容变化拒绝。恢复凭证只显示一次，不进入审计或幂等响应缓存。

## 升级与运行

旧JSON数据库在停止旧服务后先生成VACUUM快照，再在事务中重建类型列和关系行。升级检查外键，失败回滚。已应用迁移校验checksum，后续结构变化必须新增版本，不能修改旧脚本。运行中的库受PID锁约束。第三版迁移将旧版全门诊店长保留原ID、用户名及密码哈希转换为总部，并撤销受影响会话和未使用恢复码；新建店长必须分配门诊，不能以空范围获得全链权限。

服务仍为单实例SQLite设计，没有据此声称多主机写入或200并发。线上能力需目标部署和真实负载验收。Docker及备份侧车采用持久化卷，反向代理负责HTTPS；本轮已验证内容见验收记录。

## 范围说明

实现了可操作的门诊预约与运营业务。收款为人工核验后登记，恢复为机构核验后交付单次凭证；未声称银行或短信联调成功。完整临床记录、正式票据、医保等依赖另行确定业务边界和供应商接口。

# 3.1接口约定

同源JSON API；时间存ISO时间，页面按Asia/Shanghai显示；金额均为整数分。角色为customer、front、clinical、manager、hq；入口分别为/customer、/frontdesk、/doctor、/manager、/hq。

## HTTP接口

| 方法/路径 | 内容 |
|---|---|
| GET /api/health | 服务存活及数据库连接检查 |
| GET /api/portal-config | 是否显示合成数据演示入口 |
| POST /api/login | username/password/portal；身份必须与入口一致，返回user/csrfToken及HttpOnly会话Cookie |
| POST /api/register | portal=customer、username/password/name/phone；已有电话档案拒绝重复创建，转机构核验绑定 |
| GET /api/session | 当前身份与CSRF |
| GET /api/workspace | 按页面、范围、过滤及分页读取 |
| GET /api/state | 兼容验证快照，日常前端不用此接口刷新 |
| POST /api/command | type/payload；会话、CSRF、岗位与对象范围校验后事务执行 |
| POST /api/logout | 撤销当前会话 |
| POST /api/password-recovery/request | username/portal；portal为customer、front、clinical、manager或hq，无论是否存在账号均给统一结果，机构随后核验 |
| POST /api/password-recovery/consume | token/newPassword；10分钟单次凭证，成功撤销全部旧会话，不自动登录 |
| GET /api/backup | 总部业务JSON导出，包含账簿/附记/别名，不包含账号口令/会话/恢复凭证；不能用于完整恢复 |

POST写入要求application/json。已登录修改要求X-CSRF-Token。错误为error/code，服务器错误附requestId；不回传SQL、文件路径或堆栈。

## 按页查询

`page` 为home/profile/booking/appointments/history/patients/visits/settlements/resources/performance/audit/settings/accounts/finance。后端独立限制各岗位可读页面。

通用limit默认25，最大100，offset为非负整数。q为患者/账号搜索；clinicId/dentistId/status/date/from/to为相关页面筛选；date按北京时间自然日，from含、to不含。resource指定clinics/dentists/qualifications/treatments/schedules；quarter为YYYY-Q1到YYYY-Q4。booking.patientId仅取已授权患者。accounts.accountRef用于精确定位核验对象。

返回user/now/settings及当前页面需要的数组、关联lookup、pagination:{entity,total,limit,offset}。home.stats及metrics由SQL聚合，不用当前页样本推算全量统计。settlements.pendingOffset/pendingPagination独立分页未开单就诊；finance.reconciliationOffset/reconciliationsPagination独立分页营业日核对。

## 核心业务指令

患者：patient.lookup、patient.save。资源：clinic.save、dentist.save、qualification.save、schedule.save、treatment.save。预约：appointment.book、appointment.cancel、appointment.reschedule、appointment.status。诊疗：visit.save、visit.complete。开单：settlement.create。季度：cost.save、cost.review、quarter.compute、quarter.approve。规则：settings.save。

对象更新提交id及expected version（字段名version），冲突409。数据对象仍采用与页面一致的camelCase；存储层使用关系型列和子表，不要求客户端知道SQL结构。

## 补齐的业务指令

| type | payload与规则 |
|---|---|
| payment.record | settlementId,amount,method(cash/bank/pos),reference,reason,idempotencyKey；人工核对后登记，不超过欠款 |
| payment.refund | paymentId,amount,reference,reason,idempotencyKey；总部或授权门诊店长，不超过原款剩余可退金额 |
| settlement.void | id,version,reason；总部或授权门诊店长，先完整退款，追加冲销而保留原单 |
| reconciliation.preview | clinicId,businessDate；读取北京时间当日渠道净额 |
| reconciliation.record | clinicId,businessDate,observedCash/Bank/Pos,reference,reason；有差额需原因，修订追加，来源变更标记stale |
| visit.addendum | id,version,reason,content；完成后的本人接诊、授权门诊店长或总部，追加作者/时间/原版本，不覆盖原记录 |
| patient.merge | sourceId,targetId,sourceVersion,targetVersion,reason,identityEvidence；总部核验，保留别名并迁移引用，有身份或账号冲突拒绝 |
| account.bindCustomer | patientId,version,username,password,identityEvidence,reason；机构核验已有患者后绑定，不允许公开认领 |
| account.create | username,name,role,clinicIds(front/manager)或dentistId(clinical),password；总部创建员工，role可为front/clinical/manager/hq；前台和店长至少授权一家有效门诊 |
| account.assign | id,version,clinicIds或dentistId,reason；调整归属，撤销会话 |
| account.status | id,version,status(active/disabled/departed),reason；自停与最后有效总部保护，离职账号不重新启用 |
| password.change | currentPassword,newPassword；验证原密码，撤销全部会话，重新登录 |
| account.issueRecovery | id,version,identityEvidence,reason；总部核验后签发，只显示一次token，由机构交付 |

财务流水、附记、归并及核对记录不可覆盖或删除。季度收入保留有效开单口径，冲销使报告来源失效；实际收退款在独立账簿核算。

## 总部与店长边界

hq可读取全部门诊并执行全局资源、员工、患者归并、季度报告、规则、审计及导出业务。manager的clinicIds必须非空；患者关联、预约、诊疗、财务、排班和成本查询与写入均按该范围检查。店长不可读取accounts/audit/settings，不能调用全链quarter.compute/quarter.approve、全局资源维护、员工授权、患者归并/绑定或业务导出。店长performance仅返回授权门诊成本及履约统计，quarterReports为空，不泄露全链基金或其他门店金额。

## 幂等与安全

同一逻辑业务命令携带16至128位Idempotency-Key；同一用户相同key及相同内容重放原结果，不同内容409。财务payload.idempotencyKey另有独立保护命名空间，前端沿用同一逻辑UUID。响应不明时只用原始请求标识重试。

恢复码响应不进入幂等结果缓存，再次请求同一签发key返回409并要求重新核验签发；该409本身不会撤销已签发凭证，新的签发成功后旧凭证才失效。密码、token、csrf、secret不进入业务审计。账号停用、离职、改密、恢复及归属调整撤销相应会话。

# 独立部署、升级与恢复

本目录是完整应用根目录，与课程根旧Clearbrook项目无依赖。部署实例必须是单个Node服务，数据库采用本机持久化SQLite文件。以下是已提供的部署配置；实际域名、证书及云环境仍需目标环境验收。

## 发布前

执行npm ci、npm run build、npm run check、npm test、npm run test:maintenance、npm run test:browser及npm run release:manifest。只上传本目录中的源码、构建资源、文档及清单；不要上传数据库、升级快照、备份、环境秘密和测试产物。CI文件位于.github/workflows/ci.yml；本地通过不代表远端CI已执行。

## 环境配置

| 变量 | 配置 |
|---|---|
| NODE_ENV | 正式环境production |
| HOST/PORT | 本机反代用127.0.0.1/3210；容器监听0.0.0.0 |
| PUBLIC_ORIGIN | 准确HTTPS origin，多值逗号分隔，不能带路径 |
| COOKIE_SECURE | 正式环境1 |
| DENTAL_DB_PATH | 持久化且可写的数据目录，不放临时层 |
| DENTAL_SEED_DEMO | 正式新库0，关闭示例与演示按钮 |
| DENTAL_PUBLIC_DEMO | 仅公开合成数据演示时显式1，不得混入真实资料 |
| DENTAL_TRUSTED_PROXIES | 需要真实代理IP限流时填写确切可信代理地址，不信任任意来源的转发头 |

源码不会自动读取.env。可由进程管理器注入；或显式node --env-file=.env.local server/index.js。Compose从部署者的环境读取PUBLIC_ORIGIN；.env.example不含密钥。正式环境配置不完整会在打开数据库之前拒绝启动。

## 初始总部与门店授权

先设置DENTAL_SEED_DEMO=0及DENTAL_DB_PATH。通过临时DENTAL_ACCOUNT_PASSWORD环境变量输入机构选择的强密码，再运行：

```text
node tools/accounts.mjs create-staff owner hq
```

完成后删除该密码环境变量。CLI不生成示例数据。总部从/hq/login登录后录入诊所、资格、医生、治疗和排班，再创建员工并为店长、前台分配门诊。店长从/manager/login登录，只能处理明确授权门诊的业务；员工账户没有公开注册入口。顾客已有档案时走机构核验绑定；不能以知道电话为由直接认领。

## Docker与HTTPS

Dockerfile固定Node 24.15.0，非root用户运行。compose.yaml提供app与backup服务、数据与备份卷、健康检查、日志轮转和优雅停止。部署者设置PUBLIC_ORIGIN后执行docker compose up -d --build；容器端口只绑定宿主回环地址。

宿主使用deploy/nginx.conf的模板，替换域名及证书路径后核验nginx配置。代理保留Host并覆盖转发头。证书签发和域名解析属于部署环境步骤，配置文件存在不代表公网已成功。

## 升级

1. 保存代码版本和当前完整SQLite快照。
2. 停止旧Node服务。PID锁会拒绝运行中升级；容器操作应明确停止app，而不是依赖不同容器间的PID检查。
3. 启动新代码。旧JSON库自动生成pre-migration快照，在同一事务内转换表与子表并检查外键。
4. 失败会回滚；不要编辑已应用迁移来跳过checksum。后续结构变化应追加新版本。
5. 第三版迁移将原来拥有全部门诊权限的店长转为总部，原ID、用户名、密码哈希和业务归属保留，旧会话及未使用恢复码失效。原manager用户名因此可能需要到/hq/login登录；请由总部另建带门诊范围的店长账号，不要根据用户名猜测角色。
6. 完成五门户登录、总部与店长错入口拒绝、店长跨店读写拒绝、业务流程和重启持久化检查，再开放入口。

## 备份与恢复

```text
node tools/database.mjs backup <新的快照文件>
node tools/database.mjs restore <快照文件> --offline
```

恢复先校验必要结构，再在临时副本上迁移并检查外键，成功后保留旧库并替换。旧版16表快照可在副本升级为38表；新版缺表快照拒绝。恢复撤销会话与恢复凭证，避免旧Cookie恢复生效。

backup侧车默认每6小时使用VACUUM INTO生成一致快照，只在成功后按规则保留最新28份，不删除手工命名备份。工具可用--once验证一次。数据库与备份在不同卷，但仍需机构另行配置异地存储及灾难恢复；同机卷不等于异地灾备。

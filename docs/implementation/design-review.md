## 2. 本次范围与阶段对应

本次只交付真实可运行的预约闭环：微信原生 TypeScript 小程序与 Vue 3 / TypeScript 工作台共享 Node.js / TypeScript 后端和同一 PostgreSQL 数据库。保留旧程序及原 SQLite 数据；新入口不读取或写入 SQLite 业务状态。

工程采用独立 `booking-api/`，使用 Fastify、TypeScript 与 `pg` 的参数化 SQL。Fastify 负责轻量 HTTP、运行时输入校验和统一错误，应用服务组织事务，领域服务处理预约不变量，Repository 管理 SQL；不把主要业务堆到入口。共享 DTO 放在 `shared/`，Vue 与原生小程序共同使用。旧 `server/` 和 `public/` 保持 legacy 入口，不移动后冒充已完成迁移。新客户端只接新 API，不混用旧 API 或 SQLite。

## 3. 不能退让的业务规则

### 3.1 患者身份与资料

依据正文 34–35、203–210、279 页（PDF 49–50、218–225、294 页）。

- 登录账号 `users` 与实际患者 `patients` 分离，使用稳定患者编号。共用手机号、同名、生日相同均不能直接自动归并。患者账号只访问有效授权的实际就诊人。
- 课程演示至少有本人有效授权；若没有核实监护关系的流程，不允许用户仅凭手机号或患者 ID 认领他人档案。前台代约必须保留实际操作者与实际患者。
- 正式预约前核对姓名、出生日期、电话、账单地址和紧急联系人；邮箱可空。主诉是意向原述，不能作为确定诊断保存。
- 过敏状态严格使用 `known`、`none_reported`、`unknown`。`known` 至少有一条有效明细；其他两种不能由空数组自动推导。患者自述与医生核实分别记录，患者修改只能形成新的自述版本。
- `unknown` 可以预约，界面提示待医生核实；不能把未开展的临床复核写成“已排除风险”。新声明保留原版本及修改来源。
- 患者读写需要对象归属检查，不能只验证“已登录”；不得向无权者泄露候选患者详情。

### 3.2 医生、资格、服务与班次

依据正文 36–42、95–101、211–218、263–264、279 页（PDF 51–57、110–116、226–233、278–279、294 页）。

- 同一医生跨店沿用同一 `staff.id`。运营角色和总部角色不能替代专业资格。
- 服务的同一适用版本要求多项资格时，按 **全部满足** 校验。医生资格须 `verified`、在职，并覆盖整个服务区间，不仅检查查询当天或开始时点。
- 每个班次显式关联 `doctor_shift_services`；医生有资格并不意味着其每个班次自动开放所有服务。
- 门诊须运营、医生须有该门诊有效授权、牙椅须属于该门诊且可用。发布须在营业时间内；`chair_blocks` 的停用区间不能返回号源。
- 同一医生全连锁有效班次不得重叠。不同地点相邻班次须满足批准的转场缓冲，不能把两个门诊视作同地。
- 服务占用时段包含建议服务时长及必要准备、周转缓冲。预约结束字段不能只存展示的治疗时间而漏掉资源缓冲。
- 资格撤销、人员离职、牙椅停用、缩班、服务停用不能静默取消既有预约。若本次没有完整协调任务，应明确拒绝会破坏既有承诺的修改并列出影响，而非先修改再丢失预约。
- 金额以整数分保存，参考费用与最终治疗账单区别展示。临床方案、收费与价格复杂规则不扩张为本次完整诊疗功能。

### 3.3 时区与区间

依据正文 40、42、203、218–222、272 页（PDF 55、57、218、233–237、287 页）。

- 门诊 `time_zone` 为 `Asia/Shanghai`，界面按门诊当地时间展示。事件及预约起止使用 PostgreSQL `TIMESTAMPTZ`；API 传带 `Z` 或明确 UTC 偏移的 ISO 8601 时间，禁止把无偏移本地字符串当 UTC。
- 出生日期、资格有效日期使用 `DATE`，不得因时区转换前移一天。资格截止日按门诊本地日界解释并覆盖整段服务。
- 区间统一左闭右开 `[starts_at, ends_at)`；相邻 `[09:00,09:30)`、`[09:30,10:00)` 不重叠，但仍受服务缓冲和异店转场规则约束。
- 服务器时间决定查询窗口、暂占到期和取消窗口；客户端倒计时只用于提示。禁止用终端时间延长占位。
- PDF 未给固定暂占分钟数、自助取消提前小时数、查询跨度、步进或转场分钟数。这些是本次要明确记录的运行政策配置，不能宣称其数值来自设计文档。规则版本和截止时间应由 API 返回并在提交前展示。

### 3.4 号源、占位与确认

依据正文 41–44、99–104、219–224、265–266、272–275 页（PDF 56–59、114–119、234–239、280–281、287–290 页）。

1. 查询按服务资格、显式开放项目、已发布班次、营业条件、连续时长、医生全链占用、牙椅占用、停用区间与未过期暂占计算，只返回候选 DTO，不读取其他患者资料。
2. 查询不占号，查询结果附日历版本和查询时刻。无号源是可预期的空结果，不能生成虚假可选时段。
3. 确认页首先调用占位命令，暂占整组资源，生成不可猜测凭证，只保存凭证摘要，并返回 `expiresAt` 与 `holdVersion`。
4. 最终确认先认证、授权及检查幂等意图，再在短事务内按固定顺序锁资源并重读资格、班次、项目、患者资料及占位有效期。客户端字段不能替代数据库事实。
5. 同事务写正式预约、已消耗占位、确认事件、业务审计和最终幂等回执；预约初始化 `attended=false`。只有数据库提交后才能返回成功和唯一预约编号。
6. 失败整体回滚，不残留半份预约或永久占位。过期占位必须在服务器视角失效，不以后台清理任务是否恰好执行为前提。
7. 通知属于提交后的独立工作。没有接入短信或微信渠道时，不返回“已发送”；若登记本地待办，也明确显示人工待处理，不撤销已确认预约。
8. 响应丢失时小程序展示“结果待确认”，保存并重用原请求号和参数，查回执或重放同一幂等命令，不能自动换新键再预约。

### 3.5 改期、取消与状态

依据正文 45–46、105–107、219–222、272、279 页（PDF 60–61、120–122、234–237、287、294 页）。

- 取消与改期仅针对本人授权预约或员工任务范围内预约；未开始接诊，且符合统一政策窗口。临近就诊的例外不得靠任意员工或 `force=true` 绕过，必须有任务权限、理由和患者确认依据。
- 修改命令携带 `expectedVersion` 和幂等键。并发变更只接受当前版本；失败返回新状态或版本冲突，不覆盖他人操作。
- 取消保留原预约、原时段、取消类型及原因，追加事件，再释放有效资源。取消不删除预约，也不自动等同退款。
- 改期在同一事务核验新旧资源、创建新约和替代链、将旧约标记 `rescheduled`、释放旧占用并保留新占用。新资源失败或占位过期时，旧约、旧资源及其版本保持有效。
- 新旧预约患者必须相同，不能自引、不能形成环，旧约只能有一个直接后继。改期链使用 `supersedes_appointment_id`、`root_appointment_id` 与变更事件。
- 本次工作台可以查看预约状态，但不能把预约确认当成到诊或完成治疗。`attended=false` 可能为未来待到、取消、改期或未到，不得直接推断 `no_show`。未实现的接诊与完成按钮不展示。

本次选用的物理调整：新增统一 `resource_reservations` 表，集中表示患者、医生、牙椅三类资源的时间占用；`booking_holds` 和 `appointments` 指向同一预留身份。占位确认将预留从 `held` 原子转为 `booked`，取消释放，改期在事务内切换旧新预留。对 `held|booked` 状态的三类资源分别加时间排斥约束，使跨占位、正式预约的冲突也有数据库防线。字段具体表达以迁移为准，并以数据库触发器检查占位/预约与预留的资源、时段及状态关系。此方案加强了正文 220、222、272 页的跨表一致性实现，不是声称 PDF 原本就有这张表。

另外以 `clinic_services` 显式限定各门诊开放服务，并保留 `doctor_shift_services` 和有效专业资格的交集。关系、版本、权限、审计和必要唯一性不省略；非预约字段与全部临床/财务表不要求本次建齐。数据库表及字段清单会按预约范围缩小，不能声称逐字段实现整份 300 页 PDF。

约束落地要求：

- UUID 主键、明确外键、必要非空、受限状态值、`row_version>=1`、`ends_at>starts_at`。历史业务默认 `RESTRICT`，停用主档而不级联删事实。
- `users.login_name`、员工号、门诊号、患者号、预约号、服务编码、证书关联、班次服务组合有合理唯一性。患者电话不唯一。
- 外键存在不代表业务归属正确：必须另检查预约的 `clinic_id`、医生与 `shift_id` 一致，牙椅属于该门诊、服务在班次开放清单内，区间由班次覆盖；可使用相应复合唯一与复合 FK 增加数据库保障。
- 对发布班次使用 `btree_gist` 与 `EXCLUDE USING gist (dentist_id WITH =, tstzrange(starts_at,ends_at,'[)') WITH &&) WHERE (status='published')`，医生约束不按门诊分组。
- 统一预留表对患者、医生和牙椅分别加时间排斥约束；部分谓词只依据持久化的 `held|booked` 状态。取消与改期释放占用；已完成和已到诊事实保留历史区间，不靠删除解除冲突。预留状态与业务状态的映射必须在迁移与领域常量中一致。
- 仅给 `booking_holds` 和 `appointments` 各自加排斥约束，**不能**防住二者之间的冲突。选定的统一预留表消除这层盲区；仍采用统一资源主行锁协议：患者 → 医生 → 牙椅，组内按稳定 ID 排序；创建、确认、取消、改期、资源停用和班次修改均遵循同一协议，锁后重验相关业务事实。
- 可使用事务清理已到期 `held` 状态并在查询时过滤 `expires_at > serverNow`。不要把依赖 `now()` 的滚动时间条件做成自动过期的部分排斥索引；时间流逝不会自动更新索引成员。
- 改期核验目标时应在同一事务正确处理自己的旧约和目标暂占，避免旧约成为自己的冲突，同时绝不能忽略他人的占用。新旧资源全部先锁再变更。
- 权限、资格、营业状态或资源变化也要锁相同的相关资源，避免“确认刚查到有效、另一事务同时停用”竞态。简单做法是拒绝影响已有预约或有效暂占的变更，并提供影响清单。
- SQL 参数化并下推门诊、日期、资格条件；预约历史游标分页。索引按正文 267–269 页验证，不能全表读到 JavaScript 再筛选。
- 数据库迁移有版本、校验和及失败处理；演示 seed 使用合成患者及员工，不覆盖原 SQLite。集成测试使用独立 PostgreSQL 数据库。

## 5. 幂等、权限与事务协议

依据正文 265–266、272–275 页（PDF 280–281、287–290 页）。

`Idempotency-Key` 代表一次业务意图。服务器从当前身份构建 `actor_key`，唯一键为 `(actor_key, request_id)`。规范化摘要必须包含操作类型、作用范围、参数和预期版本；同键同内容重放已提交成功或业务拒绝决策，同键不同内容拒绝。

先验证当前身份和对象权限，再读取回执，防止撤权后利用旧回执读取其他人的结果。回执只保存最小必要业务引用，不把完整病史写入日志。

本地命令在一个短事务中完成 processing 回执插入、资源锁定、领域检查、业务变更、审计和最终回执提交；不预先单独提交 processing。数据库中断等暂态失败整体回滚，重试使用原键。业务拒绝可记录为稳定 rejected 决策；新意图或输入修正使用新键。唯一键并发冲突应等待并重放，而不是再建预约。

对于需要返回拒绝回执的校验，先完成纯校验，或使用保存点回滚业务子步骤后提交拒绝；不能提交部分业务以便保住错误回执。数据库排斥冲突和死锁必须转换为明确可重试/重选错误，不能捕获异常后返回成功。

| 主体 | 允许范围 | 禁止行为 |
| --- | --- | --- |
| 顾客 | 本人或经核验有效授权的患者；查询公开目录及号源 | 任意患者 ID 读写、凭电话认领、伪造员工角色 |
| 前台 | 有效门诊任务范围内患者协助和代约、查询、取消/改期 | 跨未授权门诊管理、核验医生资格、签署临床结论 |
| 医生 | 必要公开资源读取及本人职责范围；本次不扩展完整临床能力 | 将医师角色当总部管理权限 |
| 店长 | 授权门诊资源和排班维护、预约管理 | 自授总部角色或越店改班、静默取消患者预约 |
| 总部 | 有效全链任务内组织、资格、服务和资源管理 | 绕过医生资格、替代患者临床同意 |

菜单隐藏只用于体验，API 每次写入均检查身份、任务、门诊范围、对象归属、预期版本和业务状态。测试登录必须受开发环境配置限制，生产默认关闭；没有 AppID/AppSecret 时不宣称完成微信授权联调。

## 6. API 与共享 DTO 建议

参考路径来自正文 275 页（PDF 290 页）。统一版本前缀建议 `/api/v1`，下面为拟定契约，不代表接口已经实现。`treatments` 沿用文档公开路径，数据库表仍为 `services`，避免两端自行命名。

| 方法与路径 | 请求/响应要点 |
| --- | --- |
| `POST /auth/login`、`POST /auth/logout`、`GET /auth/me` | 后端会话；区分 patient/staff 场景，不接受客户端指定角色或患者 ID 作为登录凭据 |
| `POST /auth/dev-login`（若提供） | 仅开发环境开启；返回真正服务器会话，不是前端硬编码用户 |
| `GET /me/patients`、`GET /patients/{id}`、`PATCH /patients/{id}` | 显式就诊人授权；资料更新带 `If-Match`/版本，过敏声明有独立版本 |
| `GET /clinics`、`GET /clinics/{id}` | 公开地址、联系、营业时间、时区；不返回无关内部字段 |
| `GET /treatments?clinicId=` | 服务 ID、单位、参考价、时长、缓冲、自助条件；无线上能力的项目不返回可直接确认按钮 |
| `GET /dentists?clinicId=&serviceId=` | 公开姓名、专长、有效资格；不返回生日、家庭住址或证件材料 |
| `GET /booking-slots?serviceId=&clinicId=&from=&to=&dentistId=` | `startsAt`、`endsAt`、`dentistId`、`clinicId`、`shiftId`、`calendarVersion`、`estimate`、`queriedAt`；查询不返回任何他人患者资料 |
| `POST /booking-holds` | `patientId`、候选选择、资源版本；幂等键；响应 `holdId`、受控凭证、`holdVersion`、`expiresAt`、`serverNow` 和适用政策 |
| `POST /appointments/confirm` | `holdId`、占位凭证、`holdVersion`、资料/规则确认；`Idempotency-Key`；成功返回持久化预约与回执 |
| `GET /appointments?patientId=&cursor=`、`GET /appointments/{id}` | 仅本人/授权范围，稳定排序分页；返回预约状态与独立到诊事实及政策 |
| `POST /appointments/{id}/changes` | `intent=cancel|reschedule`、原因、`expectedVersion`；改期目标暂占及版本；同一 `Idempotency-Key` |
| `GET /command-receipts/{requestId}`（补充恢复接口） | 按当前身份和原对象授权查询最小命令结果；不得跨主体读取；未知请求不能伪装成功 |
| 员工 `POST/PATCH /clinics`、`POST/PATCH /staff`、资格写入/核验 | 有效总部或相应门诊任务；更新有版本 |
| `POST /treatments`、`POST /treatments/{id}/price-versions` | 总部任务、适用期间和整数分；历史价格不覆盖 |
| `GET /staff/{id}/shifts`、`POST /shifts/publish`、`POST /shifts/{id}/changes` | 有效门诊权限、全链冲突与转场校验；返回影响或拒绝原因 |
| `GET /staff-appointments?clinicId=&date=&cursor=` | 员工门诊范围内同一预约数据；代约复用 hold/confirm，不维护另一套资源池 |

共享包维护 `PatientDto`、`ClinicDto`、`ServiceDto`、`DentistDto`、`BookableSlotDto`、`CreateHoldDto`、`ConfirmAppointmentDto`、`ChangeAppointmentDto`、`AppointmentDto`、`CommandReceiptDto` 及受限状态/错误联合类型。TS 严格模式不替代运行时校验，后端仍验证所有输入。

标准错误结构：`{error_code, message, field_errors, trace_id}`。建议 HTTP 401 对应未登录，403 对应明确无权限（对敏感不存在/不可见资源可以统一 404），409 对应资源、状态、版本与幂等冲突，422 对应字段和业务资料不足。至少区分 `SLOT_TAKEN`、`HOLD_EXPIRED`、`VERSION_CONFLICT`、`REQUEST_KEY_REUSED`、`PROFILE_INCOMPLETE`、`ASSESSMENT_REQUIRED`、`SHIFT_OVERLAP`、`TRAVEL_GAP`、`CARE_STARTED`，客户端按代码提示，不靠匹配中文文本恢复。

## 9. PostgreSQL 技术依据

以下官方页面用于核对范围、排斥及部分索引机制（2026-10-22 查阅），与业务 PDF 的决定分开：

- [PostgreSQL Range Types](https://www.postgresql.org/docs/current/rangetypes.html)：`tstzrange`、半开边界、区间重叠和 GiST 排斥。
- [PostgreSQL Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)：唯一、外键及排斥约束；普通 CHECK 不负责跨行或跨表事实。
- [PostgreSQL Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html)：谓词限定索引成员，不是到期调度器。

## 2. 当前架构及接口事实

| 层次 | 已有实现 | 对迁移的影响 |
| --- | --- | --- |
| HTTP | Node 原生 `http`，在 `server/index.js` 分发路由 | 保留 HTTP 语义和错误分类，迁为模块路由与 DTO 校验 |
| 业务 | `executeCommand` 做权限、事务、命令分派、审计；业务规则已分到 service 文件 | 规则能迁移；同步 SQLite 调用不能直接复用为异步 PostgreSQL 实现 |
| 数据 | `node:sqlite`，关系表、子表，明确列映射和参数绑定 | 复用字段含义与关联检查，不复用 SQLite 存储入口 |
| 事务 | 外层 `BEGIN IMMEDIATE`，嵌套 `SAVEPOINT`；显式拒绝返回 Promise 的事务回调 | 新版必须改成同一 `pg` client 的异步事务；不能在旧事务回调直接放异步查询 |
| 页面 | ES module、字符串模板、共享状态、页面查询与全页渲染 | 复用流程与状态提示，不把 DOM 模板直接搬入 Vue 或 WXML |
| 身份 | 服务端账号密码校验，服务端 Cookie 会话、CSRF、岗位入口 | 新版仍须后端鉴权；小程序需要适配令牌传递，不能依赖浏览器 Cookie 语义 |
| 维护 | 三个已发布的带校验和迁移、备份恢复、运行锁 | 旧迁移保持不变；新版 PostgreSQL 单独版本化迁移 |

旧接口主要为：

- `POST /api/login`：`username/password/portal`，岗位必须匹配入口。
- `POST /api/register`、`GET /api/session`、`POST /api/logout`。
- `GET /api/workspace?page=...&limit=...&offset=...`：按页面授权、过滤及分页。
- `POST /api/command`：统一 `{ type, payload }`，写操作需 CSRF；可传 `Idempotency-Key`。
- `GET /api/state`：旧整包状态兼容入口。
- `GET /api/backup`：总部业务导出，不是完整可恢复快照。

旧接口没有独立的 `booking-slots`、`booking-holds`、预约确认或变更 REST 资源。新版统一 DTO 与 REST 资源契约应同时供 Vue、小程序使用，不能只更换前端接口名称而保留互不兼容的数据结构。

## 3. 可复用的患者规则

来源：`server/services/patients.js`、`shared.js`、`accounts.js`、`server/schema.sql`。

1. 患者有独立内部编号；联系电话是联系资料，不是天然的身份凭证。
2. 顾客只能维护本人档案；员工操作必须满足门诊数据范围。
3. 过敏状态明确分为 `unknown`、`none`、`known`。已知过敏至少一条逐项记录；其余状态不能残留已知过敏条目。
4. 患者自述不能自动标为工作人员核实；记录声明时间、来源及核实人。
5. 姓名、出生日期、联系电话、地址、紧急联系人与电话构成预约前资料核对要求。主动声明“未知”可继续预约，但不能显示为“明确无过敏”。
6. 已合并或停用档案不能继续改写或预约；创建来源不可被后续编辑随意改写。
7. 更新带 `version`，旧版本拒绝覆盖新资料。
8. 跨门诊查询不能由姓名模糊命中后自动认领；旧实现用电话和出生日期双条件查询，并要求唯一结果。

需要调整的一点：旧 `assertRegistrationUnique` 会因联系电话已存在而拒绝自助注册。此规则用于旧版避免重复建档，但会误伤共用联系电话的家庭成员，**不能原样迁移为患者唯一性约束**。新版账号登录标识应唯一；电话保持非唯一，实际就诊人由患者编号、会话绑定与明确身份核对确定。不得仅凭手机号声称已验证既有病历归属。

## 4. 可复用的资源与预约规则

来源：`server/services/resources.js`、`appointments.js`。

| 已有规则 | 新版处理 |
| --- | --- |
| 员工编号唯一、在岗牙医至少一项有效资格 | 保留；增加资格与具体服务项目匹配，不能“任一资格有效即可做任一服务” |
| 排班开始早于结束、未来发布、单条不超过 12 小时 | 保留可解释的时间校验；新版增加牙椅、服务时长及服务范围 |
| 同一牙医跨门诊排班不得重叠 | 保留，并由 PostgreSQL 排斥约束保证并发发布时也成立 |
| 重叠条件为 `start < other.end AND end > other.start` | 保留左闭右开语义，相邻时段可以共存 |
| 门诊、牙医、资格停用不能破坏未来有效预约 | 保留，服务端拒绝或进入明确协调流程；不能静默隐藏已约记录 |
| 已有非取消预约的旧时段不能直接改写 | 保留历史不被覆盖的原则；新版按班次与资源占用模型实现 |
| 顾客仅本人，员工仅授权门诊内代约 | 保留到查询和写入两端，不能只隐藏按钮 |
| 预约必须在未来，资源必须启用 | 查询、占位和确认都重新校验 |
| 同一牙医不能重叠接诊，同一患者不能重叠预约 | 保留，加入正式预约与有效占位的统一冲突处理 |
| 自助取消或改期遵守提前小时数，必须保留原因 | 保留，并在 API 返回规则；员工例外也需权限和审计 |
| 仅有效 `booked` 记录能改期/取消，必须校验版本 | 保留，明确新版状态名称及状态迁移 |
| 改期生成新预约，保留 `previousId` 关联 | 保留链路；失败时原预约不能丢失 |
| 预约、到诊和就诊完成分开 | 保留；本次不开发完整诊疗，不伪造完成记录 |

旧改期代码先把旧预约取消，再创建新预约，但两步位于 `executeCommand` 的同一 SQLite 事务中；新预约失败会回滚取消。迁移时必须保留这一原子性。不能只按代码先后顺序把两步拆成两个独立 HTTP 写入。

旧预约以完整 `schedule` 为预约单元，容量强制为 1。它没有短时占位、服务时长、牙椅或项目资格关联。医生已有预约检查先于容量检查，使其本质仍为每位医生每个时间区间一笔预约。新版应使用可预约时段计算与资源区间，不能把“班次剩余名额”当作完整号源算法。

## 5. 鉴权、幂等和隐私边界

来源：`permissions.js`、`shared.js`、`http/sessions.js`、`http/idempotency.js`、`http/rate-limit.js`。

- 五类入口为顾客、前台、医生、店长、总部。前台与店长有 `clinicIds`，总部全链，医生关联牙医身份。既有账号停用、调岗、密码变更会撤销相关会话。
- 密码为独立随机盐加 scrypt，比较使用恒定时间方式。数据库仅保存会话令牌散列，Cookie 为 HttpOnly、SameSite，生产要求 Secure。
- 写入先检查岗位允许的命令，再检查对象数据范围。列表筛选不能扩大数据权限；患者不能通过传其他 `patientId` 读取他人记录。
- 顾客资源目录不暴露员工出生日期、家庭住址和资格核验细节；预约列表不泄露其他患者。
- HTTP 幂等记录与业务操作同事务；同账号、同 key、同内容返回原结果，同 key 不同内容返回冲突。请求摘要包含授权范围，避免调岗后重放旧范围的敏感响应。
- 网络中断时旧前端保留原 key 和内容，显示“结果待确认”，提供核对及原请求重试。这个交互原则可复用。新版应持久保存待确认操作，避免页面重开后丢失 key。
- 结构化 request id 和客户端安全错误可复用；不能回传 SQL、系统路径、口令或栈信息。新版日志也不能记录密码、令牌与完整敏感患者资料。
- 旧生产配置拒绝缺失的 HTTPS 来源、未启用安全 Cookie、意外演示种子；新版应保留显式环境开关。测试账号应是服务端账号，不是前端伪造用户编号；正式部署默认禁用开发登录能力。

## 6. PostgreSQL 升级所需的新增保证

新架构采用 Fastify + TypeScript + `pg` 的模块化单体。Fastify 负责路由、校验、日志与统一错误转换；Service 承担事务和领域规则；Repository 使用参数化 SQL。直接使用 `pg` 可明确控制行锁、范围类型、排斥约束与事务中的同一连接，避免为课程演示引入微服务或双数据库写入。

| 旧实现不足 | 新版必须补齐 |
| --- | --- |
| SQLite 单库写事务串行化；冲突主要依赖应用查询 | PostgreSQL 中设置医生、牙椅及必要患者资源的范围排斥约束，防止两个连接同时通过检查 |
| 时间存为规范 ISO 字符串 | 使用 `timestamptz` 与左闭右开 `tstzrange`；展示统一 Asia/Shanghai |
| 无临时占位 | 占位与正式预约关联同一资源锁定机制；服务器校验截止时间，超时后释放占用 |
| 查询后立即提交整条时段 | 占位、最终确认重新校验班次、服务资格、时长、牙椅、启用状态 |
| 有幂等但非所有命令强制提供 | 对预约确认及变更明确强制命令 key，事务提交后才返回成功 |
| 资源停用与预约写入可能由不同路径并发执行 | 服务内锁定涉及的资源与班次，并以数据库约束作最后防线 |
| 改期旧模型是固定 schedule | 先取得并检查原预约版本，在同一事务完成新资源分配、旧资源释放及链路事件 |
| 单一浏览器工作区 | 原生小程序与 Vue 员工端共用同一 REST API、DTO 与 PostgreSQL，不混用 SQLite |

特别注意：有效占位由时间判断，不应直接以 `now()` 作为部分索引的动态条件。实现应采用显式占用状态和事务内过期清理等可验证机制；正式预约、有效占位不能分别约束而相互漏检。数据库约束 SQL 和并发测试必须匹配实际实现。

## 7. 旧迁移与维护规则

旧 `migrations/runner.js` 为三个版本计算 SHA-256 校验和，拒绝改写已发布迁移；迁移前检查运行 PID，非空旧库先 `VACUUM INTO` 快照。旧 JSON 结构转换、外键检查及版本记录位于同一事务，失败回滚。新版可复用这些安全目标，不能把旧 SQLite SQL 直接放入 PostgreSQL 迁移。

`tools/database.mjs restore` 要求 `--offline`、拒绝正在服务的库、校验完整表集，先在副本升级并检查，再保留原文件并替换。恢复后清理会话、恢复令牌、幂等与限流记录，防止旧凭证复活。备份调度只轮换符合自身命名规则的文件，保留手工文件。

旧 CLI `tools/accounts.mjs` 默认连接原 SQLite；不得作为新系统员工配置方式。旧 `tools/build.mjs` 包含文档构建，不能作为新架构整体构建入口。新系统需要独立启动、构建、测试和迁移命令。

本次课程演示使用新 PostgreSQL 合成数据，没有执行 SQLite 到 PostgreSQL 业务数据迁移，也不声称患者、账务、病历或资金数据已转移。未来若迁移，必须单独实现备份、字段/状态映射、主外键一致性、数量与金额校验及切换方案。

## 9. 迁移顺序与保留边界

1. 保存 Git 状态并建立独立开发分支；保留旧 `server/public/test/tools` 和数据库入口。
2. 固定新版约 300 页 PDF 及哈希，提取 UC-01 至 UC-07、数据库、接口、患者端与质量验收要求。
3. 新增独立 PostgreSQL 迁移、合成种子、共享 DTO、后端模块入口；旧 SQLite 迁移不改。
4. 迁入身份、资料与过敏、资源目录、班次发布、号源、短时占位、确认、取消和改期规则；以数据库集成测试核实并发。
5. Vue 只连新 API，验证新增班次与预约共享；原生 TypeScript 小程序接入同一 API，提供受开发配置限制的真实账号登录。
6. 联调后验证幂等、越权、失败改期原记录不丢、取消释放、跨店医生冲突、服务和 PostgreSQL 重启持久化。
7. 最后交付 Compose、Nginx、本地说明、接口、测试证据与微信人工验收步骤。

旧财务、诊疗、日结、季度激励、患者归并及恢复等未迁入能力保留在 legacy；新小程序和 Vue 不提供看似可操作的未实现入口。旧前端与新前端不共享业务状态，不建立向 SQLite 和 PostgreSQL 同步写入的双写路径。旧源码是回归参照，最终新预约闭环只以 PostgreSQL 为运行数据源。

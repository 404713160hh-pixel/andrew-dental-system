# 预约演示数据维护

演示库沿用同一套 PostgreSQL：网站管理排班和患者，小程序查询号源并管理登录患者本人的预约。号源由已发布排班、医生资格、牙椅和占用实时计算，不另建一份小程序号源。

`demo` 按来源登记补充 8 位虚构医生、8 份虚构患者档案和未来四周班次。新班次遵循两家虚构门诊的营业时间、休息日与资源冲突检查；当天只补充仍可使用的未来时段。既有班次、手动调整、已取消班次和普通记录均保留。

`demo-scenarios` 为这 8 份来源明确的虚构档案增加门诊访问关联，并经现有占位、确认、取消、改期服务建立演示预约。两个患者账号 `patient.a`、`patient.b` 可查看本人档案与预约；其他演示档案供员工端检索。账号密码保持原有配置。

每批提供 4 笔可操作的待就诊预约、1 笔取消记录，以及改期前后关联记录。固定场景键保证重复执行不重复新增；当前批次接近就诊后才生成新批次。曾撤回或失效的隐私授权不会由脚本重新接受；阻塞的演示档案会返回在 `blockedPatients` 中。新增授权夹具只用于无授权历史的虚构资料，并单独记录其合成来源。

## 本地维护

确认连接的是演示库并完成备份后，在非 production 维护进程中执行：

```powershell
npm run db:demo
$env:ANDREW_DEMO_SCENARIOS='1'
npm run db:demo:scenarios
```

生产 API 的环境和演示登录开关不变。线上独立课程演示库使用既有 `compose.preview.yaml` 的一次性维护容器；该容器明确设置 development，不能将此覆盖文件用于真实业务数据库。执行前验证目标库 `andrew_booking_preview`、来源登记及备份。禁止重置数据库或覆盖式恢复。

## 检查

本地真实 PostgreSQL 用例覆盖：来源识别、生产环境禁用、显式启用、普通同名档案与既有预约保留、重复执行、休息日和临近闭店、撤回授权不重建，以及员工与患者读取同一预约。跨端现场检查脚本为 `scripts/cloud-demo-verify.mjs`；它限定内网 Compose API 和指定演示库，凭据由环境注入，验证结束撤销自己创建的会话。
